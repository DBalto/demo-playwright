# Test Plan: Assignment Creation Workflow (Newsela Writing)

## Scope

This plan covers the end-to-end teacher flow of logging in and creating an
assignment through the 5-step "Create Assignment" modal at
`https://everwrite.app.newsela.com/assignments` (redirects to
`writing.app.newsela.com`), through to receiving a shareable assignment
link. Per the assignment brief, this is not an exhaustive spec of every
control in Steps 1-5; it focuses on the happy path plus the validation that
matters most for a teacher successfully publishing an assignment, with a
deep dive on Step 3 (the writing prompt) as requested.

Out of scope: grading/rubric scoring behavior, the student-facing writing
experience, Google Classroom integration, and non-Newsela-credential sign-in
providers (Google/Clever/Microsoft/LMS SSO).

## Environment / Test Data

- URL: `https://everwrite.app.newsela.com/assignments`
- Account: `qe.demo.teacher` (role: teacher)
- Browser: Chromium (Playwright)

## 1. Happy Path (P0 - automated in `test_assignment-workflow_spec.ts`)

| # | Step | Expected Result |
|---|------|------------------|
| 1 | Navigate to the assignments URL while logged out | Redirected to the Newsela sign-in page |
| 2 | Log in with valid `qe.demo.teacher` credentials | Redirected to the Assignments landing page |
| 3 | Click "+ Create Assignment" | Step 1 of 5 modal ("Newsela content source") opens |
| 4 | Click "Next" without adding content (content is optional) | Advances to Step 2 of 5 |
| 5 | Enter a title, set a word count range, select an assignment type, click "Next" | Advances to Step 3 of 5 |
| 6 | Review/edit the AI-suggested prompt, click "Next" | Advances to Step 4 of 5 |
| 7 | Leave the default rubric/labels, click "Next" | Advances to Step 5 of 5, showing a review of Title/Length/Type/Prompt |
| 8 | Click "Save assignment" | The "Your assignment is ready" confirmation modal appears |
| 9 | Read the "Assignment link" field | A non-empty, correctly-formatted URL (`.../editor?code=...`) is displayed and captured |

## 2. Required-Field / Validation Checks Per Step (P1)

The brief asks us to validate required steps on the modal without exhaustively
covering every scenario, so this section lists the checks worth having even
though not all are wired into the automated suite:

- **Step 1 (Content source):** Field is explicitly optional ("...or click Next
  to continue without content"). Verify Next is enabled with the field empty,
  and that an invalid URL (e.g. `not-a-url`) either shows inline validation on
  "Add" or is rejected without corrupting the following steps.
- **Step 2 (Assignment Structure):**
  - Title defaults to "Untitled" and is capped at 200 characters (counter
    shown as `n/200`) - verify the counter and that Next is still reachable
    with the default title (title does not appear to be hard-required to
    proceed).
  - Word count: verify Min <= Max is enforced (e.g., Min=300/Max=50 should be
    rejected or auto-corrected), and that non-numeric input is rejected by the
    numeric field.
  - Assignment type: exactly one of Literary Analysis / Argumentative-
    Persuasive / Narrative / Expository can be selected at a time; the
    previously selected card visibly deselects.
- **Step 3 (Prompt):** see the dedicated section below.
- **Step 4 (Assignment Configurations):** A rubric is pre-selected
  ("General Purpose Literary Analysis Grades 4-12" when no state-specific
  rubric exists) - verify Next proceeds with the default, and that changing
  the rubric updates the read-only label mapping shown further down the step.
- **Step 5 (Review):** Title is editable here too (kept in sync with Step 2);
  verify editing it here and navigating back to Step 2 shows the updated
  value (and vice versa). Verify "Save assignment" is disabled/blocked if a
  truly required field were cleared (none of Steps 1-4 appear to hard-block
  Next in normal use, so this is primarily a regression guard).
- **Cross-step:** Back/Next preserves previously entered data in both
  directions; closing the modal (X) mid-flow discards the draft without
  saving an assignment.

## 3. Step 3 Deep Dive: "Type the prompt your students will respond to"

This field deserves the most scrutiny because it is (a) AI-generated by
default, (b) a rich-text editor rather than a plain textbox, and (c) the
actual instructions students will read, so correctness here has direct
pedagogical impact. Observed behavior: Newsela's "Luna" assistant pre-fills a
leveled prompt based on the Step 2 title/type/word-count choices, in a
formatted editor (bold/italic/headings/lists/quote/undo-redo) with a live
character counter (observed max: 5,000 characters) and a "Regenerate prompt"
button.

### 3.1 Content & state scenarios

| # | Scenario | Why it matters |
|---|----------|-----------------|
| 1 | Default AI-generated prompt is present on first arrival at Step 3 | Confirms Luna pre-fill fires reliably and isn't a race condition against Step 2 data |
| 2 | Editing Step 2 (title/type) and returning to Step 3 | Does the prompt regenerate, get stale, or stay as manually edited? Users editing back and forth is a very plausible real flow |
| 3 | Click "Regenerate prompt" | A new AI prompt is produced; verify it doesn't silently fail or duplicate content, and the character counter updates |
| 4 | Manually edit the AI-generated prompt (add/remove text) | Manual edits persist through Next/Back and into the Step 5 review and the saved assignment |
| 5 | Clear the prompt entirely (empty state) | Determine whether Next is blocked, a validation message appears, or an empty prompt is silently allowed through to save (this is the single most important negative case for Step 3) |
| 6 | Whitespace-only prompt (spaces/newlines, no visible text) | Should be treated equivalently to empty - guards against a validator that only checks "is the field non-null" |
| 7 | Prompt at/near the character limit (5,000) | Verify the counter is accurate, typing is blocked or truncated at the limit rather than silently dropping characters, and paste-in-excess-of-limit is handled |
| 8 | Very long prompt pasted in one action (e.g., 10,000 chars) | Checks paste-path validation vs. type-path validation, which can diverge in rich-text editors |
| 9 | Special characters, emoji, and non-Latin scripts (e.g., `<script>`, `"quotes"`, `é/ñ/中文`, emoji) | Confirms the editor sanitizes/escapes rather than executing or corrupting input (basic XSS/encoding hygiene), and that the character counter counts consistently across Unicode |
| 10 | Formatting toolbar actions (Bold, Italic, H1/H2, bulleted/numbered list, Quote) applied to part of the prompt | Formatting is preserved through Next → Back → Next, into Step 5 review, and into what the student ultimately sees |
| 11 | Undo/Redo after typing and after Regenerate | Confirms the editor's undo stack behaves predictably and doesn't let a user "undo" into a broken/half-rendered state |
| 12 | Navigate Back to Step 2, change the title, then Back further is not needed - go directly Next again to Step 3 without regenerating | Prompt text a user already edited should not be silently overwritten by a fresh AI generation |
| 13 | Rapid double-click / repeated clicks on "Regenerate prompt" | Guards against duplicate in-flight AI requests or a race that leaves the editor in an inconsistent state |
| 14 | Keyboard-only interaction (Tab into editor, type, Tab to Next) | Accessibility: the rich-text editor and toolbar should be operable without a mouse |

### 3.2 Recommended automation coverage

Given the 1-2 hour scope, the automated suite implements the default-prompt
happy path (case 1) as part of the full E2E flow, plus targeted checks for
cases 5 (empty prompt), 7 (character limit boundary), and 9 (special
characters), as these carry the highest risk (data loss / broken assignments
for students) relative to effort. The remaining cases are documented here as
the natural next slice of coverage.

## 5. Accessibility Observations (informational, not blocking)

While building the Page Object Model it was observed that several fields
(assignment title, min/max word count) do not expose a proper
`<label for>`/`aria-labelledby` association - their accessible name resolves
to placeholder text ("Type here") rather than the visible field heading,
which is ambiguous for screen-reader users and for label-based test
locators. Recommended as a low-effort a11y fix; noted here since it directly
affected how the Page Objects had to locate these fields (see comments in
`pages/CreateAssignmentModal.ts`).

## 6. Security Observation: Login Form Submission Method (informational)

While automating login, the sign-in form was observed - under fast,
programmatic input (values set in one shot rather than typed keystroke by
keystroke) - to occasionally fall back to a plain HTML form GET submission
instead of the app's JS-driven sign-in handler, navigating the browser to
`https://app.newsela.com/signin/?username=...&password=...` with the
username and password as **plaintext URL query parameters** (and therefore
exposed in browser history and, plausibly, server access logs). The
automation was hardened to type character-by-character and wait for the
submit button to report enabled before clicking, which avoids the race in
practice. This is still worth a manual/security follow-up independent of the
automation workaround: a real user pasting credentials via a password
manager (which also sets the value in one shot rather than typing it) could
plausibly trigger the same fallback path.

## 7. Out-of-Scope / Follow-Up Ideas

- Multi-tab/session conflict (editing the same assignment from two tabs)
- Network failure mid-save (assert no duplicate assignment is created on retry)
- Assigning to an actual class/roster and the student-facing submission flow
- Internationalization of the AI-generated prompt for non-English rubrics
